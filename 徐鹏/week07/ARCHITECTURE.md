# ARCHITECTURE.md — 技术方案文档

> **一句话结论**：这是一个「金融公告 → 结构化事件」的**信息抽取**教学项目。同一个任务，用
> **规则 → 无预训练 BiLSTM-CRF → BERT 序列标注（联合/两段式）→ LLM 提示 → LLM 微调 → 系统组合**
> 六层做法各实现一遍，**全部在同一批 dev 数据、同一套评测函数上出数字**，用数字说明
> 「什么地方该用模型、什么地方规则反而更靠谱、什么地方必须上大模型」。

读完这份文档你应该能回答三个问题：

1. 事件抽取的输入输出到底是什么（schema、触发词、论元、span 对齐）；
2. 六层做法各自的技术选型理由、实测效果、失败模式；
3. 做这个任务真正会踩的 33 个工程坑（不是"理论上"的坑，是本项目实际踩过并写进代码的坑）。

## 1. 项目定位

### 1.1 为什么选「事件抽取」，而不是继续做分类 / NER

| 维度 | 文本分类 | NER（序列标注） | **事件抽取（week7）** |
|---|---|---|---|
| 输出 | 一个标签 | 一段文本里若干 (实体, 类型) | **一个事件 = 类型 + 触发词 + 若干「角色 → 论元」** |
| 难点 | 类别不均衡 | 边界定位 | **边界定位 + 角色归属 + 事件计数**，三者叠加 |
| 工程味道 | 中 | 中 | **强**：schema 约束、校验、人工复核、篇章合并 |
| 简历含金量 | 中 | 中 | **高**：信息抽取是最像"业务落地"的 NLP 任务之一 |

**一句话结论**：分类只需判断"是什么"，NER 只需找到"哪些词"，而事件抽取要同时回答
**"发生了什么事（类型）、凭什么这么说（触发词）、涉及谁/多少钱/什么时候（论元）"**——
它天然包含"结构化输出 + 业务校验"，是投研/风控/舆情产品的核心组件。

### 1.2 场景选型：为什么是金融公告

| 候选场景 | 域适配 | 数据可得性 | 结论 |
|---|---|---|---|
| 通用领域事件（DuEE 1.0） | 只有"财经/交易"等少数类型与投研相关 | 易得 | ❌ 域太泛，和产品主线接不上 |
| **金融公告事件（DuEE-Fin）** | **13 类全是上市公司公告高频事件**（质押/回购/减持/增持/收购/上市/融资/中标/亏损/破产/高管变动/被约谈/解除质押） | 公开镜像可下载 | ✅ **本项目采用** |
| 自建标注 | 完美 | 需要标注成本 | ❌ 教学项目不现实 |

**任务口径（重要，本项目实际交付的任务定义）**：DuEE-Fin 原始发布是**篇章级多事件**标注（一篇公告 1~12 个事件）；
本项目把它**派生成「一句公告 → 一个事件」的句子级任务**，也就是课件包里 `data/processed/train_extract.jsonl`
的形态：**一行 = 一句原文 + 恰好 1 个事件（类型 + 触发词 span + 若干「角色 → 论元 span」）**。

为什么做这个转换（不是为了省事，是标签体系决定的）：
1. **一条 BIO 序列只能表达一个事件**——联合方案是 149 标签的单条序列，同一字符位置只能有一个标签；
   而篇级数据里 **29% 的篇多事件**，其中**约 42% 的篇存在「同一角色多个不同取值」**（两个回购事件各有回购方/金额），
   塞进一条序列必然互相覆盖。
2. **位置上限**：篇长中位 500 字、p90 650、max 3,485，而训练用 `max_len=256`（BERT 硬上限 512）——
   整篇直喂会有 **79% 的篇被截断**（>512 字的有 42.7%），尾部事件直接丢。
3. **训练/推理输入分布一致**：句级样本中位 161 字；分发粒度变化会直接掉点（本项目实测：按标点切成 15~30 字碎片
   → 一篇金标 6 事件抽出 0 个）。

所以：**模型主线只对「一句一个事件」负责**；`train_detect`（32,794 句含负样本）负责判「这句有没有事件」，
`dev_docs`（985 篇）负责系统层的「切句 → 逐句抽 → 事件流」演示 —— 多事件/篇章级能力放在系统层，而不是塞给单条标签序列。

**选它的三个理由**：

1. **同域**：和本期课程的贯穿产品「八斗投研工作台」完全同域——把公告变成事件流，是投研产品的第二块拼图。
2. **标注结构刚好**：自带「事件类型 + 触发词 span + 论元 span」，字符级 offset 现成，能直接喂给 BIO 序列标注。
3. **规模适中**：句子级单事件 train 5,747 / dev 930，一张 8GB 显卡几十分钟能跑完一轮，课堂上能现场出数字。

> 数据许可：DuEE-Fin 来自公开竞赛，协议限**非商业科研/教学**用途，且未授权再分发。
> 因此课件包**只发派生数据**（完整 `data/processed/` + 快速冒烟用的 `data/sample/`），原始发布文件 `raw/` 不发
> （详见 `data/DATA_REPORT.md` §12 与 `data/README.md`）。
>
> **完整数据下载渠道 + 重建步骤**：见 **[`data/README.md`](data/README.md) §6** ——
> 官方千言（https://www.luge.ai/ 搜 `DuEE-Fin`，需登录）或本项目实际使用的 GitHub 镜像 `maopademiao/duee_fin`；
> 下载 5 个原始文件按约定命名放进 `data/raw/DuEE_Fin_mirror/`，再跑 `build_dataset.py` + `verify_processed.py`。
> `data/sample/` 里 7 个文件各是什么、谁在用，见同文档 §2.1 的表。

### 1.3 六层方法一览（本项目的"主线"）

| 层级 | 方法 | 脚本 | 一句话定位 |
|---|---|---|---|
| **L0** | 规则：触发词词典 + 正则 + 公司名词典 | `rule/run_rule.py` | 最诚实的对照组：不训练能拿多少 |
| **L1** | 字符级 BiLSTM-CRF（无预训练） | `bilstm_crf/train.py` + `common/crf.py` | 量化"预训练值多少个点" |
| **L2a** | BERT 序列标注（联合 BIO，149 标签） | `bert/train.py` | 本周主线：一个模型端到端 |
| **L2b** | 两段式：检测 → 类型 → 类型条件论元 | `bert_pipeline/train.py` | 本周核心对比：拆开到底更准吗 |
| **L3** | LLM zero-shot / few-shot | `llm_zero_shot/llm_extract.py` | 不训练、靠提示能到哪 |
| **L4** | LoRA SFT（Qwen3-0.6B） | `llm_lora/train_sft.py` / `evaluate_sft.py` | 小模型 + 少数据能不能超过提示 |
| **L2 技巧** | **CRF 硬约束解码**（不重训，只改解码） | `bert/evaluate_hard_constraint.py` | **本周最强一格**：论元 F1 +7.5pp |
| **L5** | 系统组合：切句→检测→抽取→正则兜底→校验→篇章合并 | `service/extract_service.py` | 模型指标 ≠ 能上线，差在哪 |

## 3. 各环节技术选型

### 3.1 标签体系：joint（149 标签）vs typed（11~19 标签）

**一句话结论**：联合模型标签多、一次前向搞定；类型条件模型标签少、单标签样本密度高，
但**必须先知道事件类型**——这个取舍就是"联合 vs 两段式"的全部内容。

| | joint（联合） | typed（类型条件） |
|---|---|---|
| 触发词标签 | `B- TRG:股份回购`（带事件类型） | `B-TRG`（类型由外部传入） |
| 论元标签 | `ARG:交易金额`（61 个角色跨类型共享） | `该类型专属的角色名`（4~8 个） |
| 标签总数 | `1 + 2×(13 + 61) = 149` | `1 + 2×(1 + roles(t))`：被约谈 **11**、公司上市 **19** |
| 一次前向 | 类型 + 触发词 + 论元全出 | 只能出触发词 + 论元（要先给类型） |
| 适合谁 | `bert/train.py`（L2a） | `bert_pipeline/train.py` 的第三段（L2b） |
| 代价 | 长尾角色的样本被摊薄（很多角色训练样本不到 100） | 类型判错 → 论元全错（误差累积） |

**为什么论元不按类型再拆一层（joint 里）**：拆开标签数会从 149 涨到 200+，而「披露时间」
「交易金额」这类角色本来就在 13 个类型里通用。共享之后每个标签能见到**更多训练样本**，
长尾角色不至于跌破两位数——这是小数据集上很实际的取舍（`common/event_data.py` 的注释里写明了）。

跑一下就能看到这套标签体系：

```bash
python common/event_data.py
# schema: {'num_types': 13, 'num_type_role_slots': 92, 'num_union_roles': 61}
# joint 标签数 = 149（O + 2×74 实体标签）
# typed[公司上市] 标签数 = 19 → ['O','B-TRG','I-TRG','B-上市公司',...]
# 数据规模: {'train_extract': 5747, 'dev_extract': 930, 'train_detect': 32794, 'dev_detect': 5302, 'dev_docs': 985}
```

### 3.2 span → BIO 与 BERT 子词对齐（最容易错的一步）

**一句话结论**：序列标注里 token 数**不一定等于**字数，标签必须能贴回每个字；只有**首个子词**
背标签，其余子词与 `[CLS]/[SEP]/[PAD]` 全部设 `-100`（不算 loss）。

> **实测事实（2026-11，避免照着网上的例子想当然）**：`bert-base-chinese` 对中文基本**一字一 token**
> （`"质押" → ["质","押"]`）；dev 930 句 154,318 字 → 152,858 token、**`##` 子词 0 个**，
> 网上常举的「质/##押」在这个词表上并不存在。真正让 token≠字的是：特殊符、**空格/换行不产生 token**、
> `[UNK]`（本数据 3,026 个，连 `IPO` 都是 UNK）。只有**不逐字、整句 tokenize** 时数字/英文才会被切成
> `005 + ##10`；换 Qwen 这类 BPE 词表时中文反而会多字合成一个 token（`股份回购` → 2 个）。

流程（`common/event_data.py: BioDataset`）：

```
text（"中教控股收购海南学校"）
  → span_to_char_tags()：逐字符刷 BIO，先刷论元、最后刷触发词（触发词优先，因为它决定类型）
  → tokenizer(list(text), is_split_into_words=True)：把一个汉字当一个 word
  → word_ids()：token → 第几个汉字
  → 首子词保留标签；非首子词 / 特殊 token → -100
```

**为什么必须这样做**：`-100` 是 PyTorch `cross_entropy(ignore_index=-100)` 的约定值
（CRF 里则要靠 `mask` 额外屏蔽）。在本项目「逐字输入 + bert-base-chinese」的组合下，它主要挡掉
特殊符与缺失 token 的位置；而一旦你改成整句 tokenize、或换成会把词合并的 tokenizer，
同一个字的非首子词就会真的出现 —— 不写这段对齐，标签会静默错位、指标虚高，而且很难查。

**动态 padding**：`collate_bio` 只补到**本 batch 最长**，不是全局 `max_len`。
本数据集句子平均 164 字、最长 797 字，按 `max_len=256` 静态补齐等于每条都算满 256 token；
动态补齐后平均只算 ~170 个，**训练速度约 1.5 倍且效果不变**——这是 NLP 训练里最便宜的一次提速。

### 3.3 解码器：Linear vs CRF，以及"CRF 为什么不保证零非法序列"

**一句话结论**：CRF 的价值不是"涨点"，而是**把非法 BIO 序列显著压下去**；它靠学出来的
转移矩阵"倾向于"合法，**不是硬约束**——要真的归零，必须显式屏蔽非法转移。

| | BERT + Linear | BERT + CRF |
|---|---|---|
| 解码 | 每 token 独立 `argmax` | 维特比全局最优路径 |
| 参数 | 无额外参数 | `(149×149)` 转移矩阵 + start/end 分数 |
| 非法序列 | 会喷（`I-x` 开头、`B-x` 接 `I-y`） | **明显减少**，但不为 0 |
| 归零手段 | 只能后处理修 | `--hard_constraint`：非法转移分数置 `-1e4` |

`common/crf.py` 是**手写**的（不依赖 `pytorch-crf`），三个公式都在 log 空间算：

```
路径分数  S(y|x) = Σ_i emit_i[y_i] + Σ_i T[y_{i-1}][y_i] + start[y_0] + end[y_L]
配分函数  logZ   = log Σ_{所有路径} exp(S)      ← 前向算法，O(L·C²)，用 logsumexp 不是 max
损失      loss   = logZ − S(金标路径)            ← 负对数似然
解码      维特比：每步只留最优前驱 + backpointer 回溯
```

**两个易被想当然的点，本项目都做了实证**：

1. **只加转移约束不够**：序列第一个 token 是 `I-x` 这件事转移矩阵管不到，
   必须再有 `start_constraint`。`build_start_constraint_mask()` 的注释记录了实测：
   **只加转移约束时非法开头仍有 42%**。
2. **手写实现要验算**：`crf.py` 用暴力枚举全路径验证前向 `logZ` 与维特比最优路径，
   **误差 0.00e+00**；用随机 emission 跑无约束解码，每条序列平均 **12.2 处**非法转移，
   加上硬约束后**严格 = 0**（这两组数是本项目自检脚本实测，见 `data/DATA_REPORT.md` 与 PPT）。
3. **"约束只是让输出好看"是错的**：同一个 CRF checkpoint，只把解码期的非法转移 mask 成 `-1e4`、
   重跑维特比（**不重训、decode 90 秒**），论元 F1 **0.5815 → 0.6566（+7.5pp）**、
   事件级 **0.1697 → 0.2177（+4.8pp）**。说明**非法解码本身在破坏 span 边界**，
   约束是准确率的一部分（详见 §4.9）。

### 3.4 两段式 vs 联合：为什么拆开可能更准，也可能更差

**一句话结论**：拆开（检测 → 类型 → 类型条件论元）把标签空间从 149 缩到十几，
**论元边界能学得更准**；但类型判错会让论元全错，且延迟是 3 倍、要维护 15 个模型。

| | 联合（`bert/train.py`） | 两段式（`bert_pipeline/train.py`） |
|---|---|---|
| 模型数 | 1 | 1 检测 + 1 类型 + 13 专家 = **15** |
| 标签空间 | 149 | 11~19（每个类型一个专家） |
| 一句话几件事 | 一次前向 | 三次前向（检测/类型/论元） |
| 误差累积 | 无 | **有**：类型错 → 论元必错 |
| 显存占用 | 1 × BERT | 13 × BERT（专家只留 4 层 ≈ 182MB/个） |
| 定位瓶颈的手段 | 看 per_role F1 | 看诊断字段：`n_detect_dropped` / `n_type_wrong` / 类型准确率 |
| 上界分析 | 无 | `pipeline_oracle_type`：类型给金标 → 隔离出"类型错"造成的损失 |

两段式的第三段刻意用**线性头而不是 CRF**：每类标签只有十几个，非法序列问题本来就小，
加 CRF 的收益不抵训练/推理成本（`bert_pipeline/train.py` 顶部注释写明这个取舍）。

### 3.5 规则基线：为什么它必须存在，而且必须"诚实"

**一句话结论**：规则能在**有规律的字段**上打败模型（金额/日期/比例），却在**自由文本字段**
上一败涂地（公司名、标的物）——它给后面的模型提供了明确的"该解决什么"的靶子。

规则系统的四段（`rule/run_rule.py`）：

1. **触发词**：从 train 统计出现 ≥2 次的 trigger 文本（去噪）+ 一小张人工同义词表；
   匹配时**最长优先**（否则「质押」会抢走「解除质押」，类型直接错）。
2. **数值类论元**：按角色名语义归类（含"金额/价格/亏损"→ 金额正则；含"时间/日期/周期"→ 日期正则…），
   正则先试"区间"再试"单值"（`1.2亿元至1.5亿元` 是一个论元，不是两个）。
3. **公司/机构类论元**：用 train 标注过的公司名建词典 + `…有限公司/…集团` 后缀正则。
4. **每个角色只领一个、按出现顺序依次填充**：这条简单规则恰好吻合公告写法
   （「甲公司收购乙公司」里 收购方在前、被收购方在后），也把假阳性压下来
   （注释记录：不做这个限制时 argument 精确率只有 0.13）。

规则基线的实测价值在**失败分布**（见 §4.2）：触发词命中率 **99.8%**，事件级只对 **1.5%** ——
**"能判类型、填不满槽位"**，这就是"为什么必须上序列标注模型"的最直观答案。

### 3.6 生成式抽取：为什么不让模型输出 offset

**一句话结论**：让模型只输出**原文片段文本**，位置由程序 `text.find()` 反查——
因为生成式模型算字符下标极不可靠，而"逐字抄一段原文"对它很容易。

| 做法 | 风险 | 本项目选择 |
|---|---|---|
| 模型输出 `start/end` | 中文"字符数 ≠ token 数"、从 0 还是 1 数全凭模型心情，一处错位整个 span 就废 | ❌ 不用 |
| 模型输出文本 + 程序 `find()` | 同一片段多次出现时取首次，高亮位置偶有偏差（**有意的近似**） | ✅ 用这个 |

配套的三层容错（`llm_zero_shot/event_prompt.py`）：

```
剥 ```json 围栏           → _strip_code_fence()
括号配平截取第一个 JSON     → _first_json_object()（正则贪婪/非贪婪都会挂，必须配平扫描）
被 max_tokens 截断时补全   → _close_truncated()（补引号 + 补右括号，宁可丢最后一个论元）
```

每一步都记账：`json_valid_rate / repaired / empty_reply / type_invalid / role_invalid /
trigger_not_in_source / arg_not_in_source`。**这些"工程指标"比 F1 更能说明生成式抽取的成本**。

### 3.7 系统组合：模型指标不错，为什么还不能直接上线

**一句话结论**：真实系统 = 模型 + 规则兜底 + schema 校验 + 人工复核 + 篇章合并；
`service/extract_service.py` 把这五件事串起来，并给每一步留下可解释的标记。

| 环节 | 做什么 | 为什么 |
|---|---|---|
| `split_sentences()` | 按 `。！？；\n` 切句，**保留偏移** | 篇章输出必须能定位回原文（高亮/溯源） |
| `extract_sentence()` | 联合模型 或 检测→类型→论元 | 两种后端可切换，便于对比 |
| `_validate()` | 角色必须属于该类型；论元必须能在原文找到；去重 | 防"幻觉式结构化输出"——schema 不合规的角色直接拦掉 |
| 正则兜底 | 模型没抽到的金额/日期/比例/股数用正则补，标 `source="regex"` | 数值类字段有强规律，正则比模型稳且可解释 |
| `_needs_review()` | 低置信 / 无事件 / 缺核心角色 / 枚举值不合法 → 标人工复核 | 真实业务"机器抽 80% + 人审 20%"比"全自动但 15% 错"更可行 |
| `extract_document()` | 同类型事件合并成事件流，论元累加去重，记 `sent_ids` | 一篇公告最终输出 1~3 个事件流，而不是 7 个碎片事件 |

### 3.8 评测口径：为什么必须只有一个评测函数

**一句话结论**：`common/evaluate_events.py` 是全项目**唯一**的评测实现；各脚本
只负责产出预测 JSONL，指标一律由它算——否则"谁更好"这件事不可信。

三级指标（本项目所有表格都用这一套）：

| 指标 | 判定 | 用途 |
|---|---|---|
| **trigger** P/R/F1 | 触发词**文本**完全相等（不看类型） | 看"有没有找对词" |
| **argument** P/R/F1 | `(角色, 论元文本)` 二元组集合比对（多抽算 FP、漏抽算 FN） | 最常用的论元级指标 |
| **event_exact** P/R/F1 | 类型 + 触发词 + 论元集合**全等**才算对 | 最严格；只报它会显得很低 |
| **type_macro_f1** | 只看事件类型，把 `(样本, 类型)` 当集合算 13 类 macro | 对比两段式第一段有多准 |
| per_type / per_role | 分组指标 | 定位瓶颈（长尾类型、难角色） |

三条口径纪律（写进代码注释，也写进 PPT）：

1. **解析失败/空输出的行必须留在预测文件里**（`events: []`），删了分母变小、F1 虚高；
2. **评测键是 `id|sent_id` 而不是 `id`**（DuEE-Fin 的 `id` 是文档 id，不唯一）；
3. **跨方案比较必须同批样本**：LLM 侧固定 n=200 抽样（`outputs/llm/eval_ids.json`），
   判别式方法把全量预测**投影到同一批 200 条**再报一份（`eval_utils.evaluate_nested_subset`）。

## 3.9 训练日志体系（学生课后复看训练过程）

**为什么单独做这件事**：课上 2.5 小时要讲 6 种方法 + 对比 + 系统组合，**没有时间现场把训练跑一遍**。
但"训练过程"恰恰是初学者最陌生、也最想看的：loss 怎么降、每个 epoch 多久、验证集哪一轮最好、
显存峰值多少。所以每个方法跑完都留一份**结构化日志**，学生下课后可以自己复现、自己画曲线。

### 三类文件（训练类方法）

| 文件 | 内容 | 回答什么问题 |
|---|---|---|
| `outputs/logs/<method>_train.json` | `argv`、`args`（超参）、`env`（python/torch/GPU）、`params`（参数量）、`epochs[]`（每轮 train_loss / 内层验证指标 / 耗时）、`total_elapsed_s`、`peak_gpu_mb`、`finished`，以及收尾字段（`best_epoch` / `dev_metrics` / `illegal_dev`…） | 「这次到底用了什么参数、跑了多久、最好在哪一轮」 |
| `outputs/logs/<method>_steps.jsonl` | **每 `--log_every`（默认 50）步一行**：`{"epoch","step","loss","lr","elapsed_s","step_elapsed_s"}`（两段式的行还带 `stage` 区分是哪一段） | 「loss 是怎么降的」——画曲线、看有没有发散/平台期 |
| `outputs/logs/<method>_console.log` | 该次运行的完整 stdout | 「当时屏幕上一共打印了什么」——排错用 |

纯评测方法（`rule/`、`llm_zero_shot/`、`bert/evaluate*.py`、`llm_lora/evaluate_sft.py`）不训练，写
`<method>_eval.json`（`argv`/`args`/`env`/`runtime_s`/`metrics` + 该方法特有统计）+ `<method>_console.log`。

实现集中在 **`common/log_utils.py`**（`TrainLogger` / `EvalLogger`），所有方法共用同一份，
保证「同一套字段口径」——`eval/compare_methods.py` 与 `eval/compare_to_numbers.py` 才能统一读。
`--log_every` 只在训练脚本里有，想看得更细就 `--log_every 10`。

### 学生怎么用（画 loss 曲线）

```python
import json, matplotlib.pyplot as plt

plt.plot([r["elapsed_s"]/60 for r in rows], [r["loss"] for r in rows], marker="o", ms=3)

```

> 线性头是交叉熵，量纲完全不同。要比就看**曲线形状**与 `epochs[].val` 里的验证指标。

> **口径说明（prompt v2）**：API 侧数字用**修复 schema 分隔符后的 v2** 重跑；v1（用 `/` 分隔角色名）
> 的零样本是 trigger 0.8060 / argument 0.5184 / event 0.0605，仅用于说明「prompt 工程」的价值，不进正式表。
>
> 以下所有数字由 `common/evaluate_events.py` 在同一份
> `data/processed/dev_extract.jsonl`（930 句，句子级单事件）上算出。
> 另有 `n=200` 子集口径（`outputs/llm/gold_n200.jsonl`，dev 排序后 `shuffle(seed=42)` 取前 200），
> 用于和 LLM 链路并排比较。**没跑的实验标「未跑」并写清原因，绝不填估算值**；
> 所有格子都来自 `outputs/metrics/**/*.json` 的真实产物（可逐条反查命令行）。

### 4.1 主表：六层方法在 dev 930 上的表现

> **读表提醒（重要）**：规则的 `type_macro_f1` 反而**比 BERT 高**（0.8118 vs 0.7654）——
> 它用触发词词典直接定类型，命中就很准；BERT 端到端学 149 个标签，类型会被长尾角色拖累。
> 只看 type_macro 会得出"规则比 BERT 好"的荒谬结论，**论元/事件级上规则是被碾压的**。
> 这就是"指标要选对"的最好例子。
>
> **两段式（第 6/7 行）跑的是「压缩配置」**：检测器、类型分类器、13 个专家确实都训出来了（16 个模型、
> 49.87 ms/句），但端到端只有 **0.6769 / 0.3690 / 0.0957**，**明显低于联合模型**。
> 原因不是「两段式方法不行」，而是**训练预算被切碎**：13 个专家每个每 epoch 只有 **3~31 步**（3 epoch 也才 90 步量级），
> 而联合模型有 **486 步**。诊断数据支持这个解释：检测器 F1 **0.7740**（丢 255 句）、类型准确率 **0.9452**（错 51 句）、
> 论元截断 101 句 —— 检测+类型两段本身是好的，**损失在第三段专家的欠训练**上。
> 金句：**流水线拆得越细，每个子模型分到的训练步数越少；两段式的隐性成本不是推理延迟，是「训练预算被切碎」。**
> 类型给金标的上界（第 7 行）只把 trigger 从 0.6769 提到 0.6861、论元几乎不动，进一步证明瓶颈不在类型而在论元专家。
>
> **⚠ 第 6/7 行是 2026-11-16 的值，11-18 这轮没有重跑成功**（数字照旧，日志也沿用旧的）：
> 代码侧的 bug 已修好并用 `--mock` 验证（`_steps.jsonl` 能正常写、每行带 `stage` 字段），
> 但真跑时**检测器（8000 条 / 125 个微批）跑了 19 分钟仍未完成**（≈9 s/微批，
> 同期 `bert/train.py` 只要 ~0.5 s/微批），在当晚的时间窗内无法完成，于是保留旧值、不新造数字。
> 复跑命令（与上表同配置）：
> ```bash
> python bert_pipeline/train.py --detect_limit 8000 --cls_epochs 1 \
>        --arg_epochs 3 --arg_lr 8e-5 --arg_layers 4
> ```
> 详见 `outputs/logs/README.md` 的「本轮日志可用性清单」。
>
> **L4 反超判别式（本表最重要的一行）**：LoRA SFT 在**同一批 n=200** 上 argument **0.6971**，
> 比硬约束 BERT（0.6418，n=200 口径）**高 5.5pp**、比 API few-shot（0.5347）高 16pp；
> 但 event_exact（0.1850）仍低于硬约束 BERT（0.2268，n=200）
>
> ⚠ **2026-11-18 重跑新增发现**：LoRA 的 `type_macro` 从 0.7862（原 0.9150）**下降不是随机噪声**——模型输出了 13 类之外的名称（如「公司回购股份的进展公告」「回购」），把 macro 的分母从 13 撑到 15+。判别式标签空间封闭、不会犯这个错；**生成式抽取必须做「类型白名单 / schema 合法性」校验**（对应 PPT 五道校验页）。——**生成式在槽位召回上更强、在边界精确上更弱**。
> 注意 LoRA 只跑了 n=200，没有 930 全量口径，报告里不要把它和 930 的行混排。
>
> **「预训练到底值多少点」的两个台阶**（`compare_methods.py` 自动算，可复现）：
> 规则 **0.1740** → BiLSTM-CRF **0.4634（+28.9pp）** 是「有建模」的收益；
> BiLSTM-CRF **0.4634** → BERT+CRF **0.5815（+11.8pp）** 是「有预训练」的收益。
> 注意 BiLSTM 这条是为控时间用 `max_len=128` 跑的（dev 截断 **67.1%**），所以它的数字**偏保守**——
> 报告里必须写这个口径，否则会把「CRF 比 BERT 差」的一部分原因错算到模型头上。
>
> **读第 6/7/8 行前先看口径**：第 8 行（LoRA）是 **n=200** 子集，第 6/7 行是 dev 930 全量；
> 两者并排只用于「方法量级」对照，正式对比见 §4.10 的同批 n=200 表。
>
> **CRF 值不值得**：同一训练预算下 CRF 每一轮都略优（见 §4.8），最终论元 F1 **+1.85pp**、
> 事件级 **+1.33pp**；代价是训练**慢 5.9 倍**、推理**慢 3.3 倍**（12.26 → 40.92 ms/句）。
> 这是"精度 vs 延迟"天平上的真实数字——生产环境要不要上 CRF，取决于你的吞吐要求。
>
> ⚠ **耗时口径（重要）**：上面的 **5.9×** 取自**首跑**（11/16，机器上无其它任务）**531 s → 3112 s**。
> 11/18 重跑时 CPU 上同时跑着 `bilstm_crf`（3 epoch），两条 BERT 的 tokenize/dataloader 都被争用，
> 实测变成 637 s / 2742 s（**一升一降，方向都不一致**）→ **不能用来重算倍率**，
> 主表里的 637 / 2742 只表示"该次运行的实际情况"。

### 4.2 规则基线的失败分布（已实测，这是"为什么要上模型"的一页）

| 错误类别 | 条数 | 占比 | 含义 |
|---|---|---|---|
| `arg_spurious` | 517 | **55.6%** | 金额/日期乱填到错误角色（规则分不清"哪个数字属于哪个角色"） |
| `wrong_trigger` | 214 | **23.0%** | 类型判对了，触发词文本/边界不对 |
| `wrong_type` | 141 | **15.2%** | 触发词命中但类型错（典型：「质押」抢「解除质押」） |
| `arg_missing` | 41 | 4.4% | 事件对了但论元漏抽 |
| `exact` | 15 | **1.6%** | 完全正确 |
| `no_trigger` | 2 | 0.2% | 整句没扫到触发词 |

- **触发词命中率（整句有事件的比例）= 99.8%**
- **一句话结论**：规则**能判类型**（type_macro 0.81）、**填不满槽位**（argument 0.17）。
  论元这 0.17 就是 L1/L2 序列标注模型要抢回来的分数。

### 4.3 LLM 链路（L3）：固定 n=200 子集

| 方法 | 条数 | JSON 合法率 | 空回复 | trigger F1 | argument F1 | event F1 | type_macro F1 | 平均延迟 | token 总量 |
|---|---|---|---|---|---|---|---|---|---|
| API zero-shot（`deepseek-v4-flash`） | 200 | **100%** | 0 | **0.7789** | **0.5224** | **0.0402** | 0.9281 | **3.62 s** | 191,578（prompt 169,891 + 生成 21,687） |
| API few-shot（6 例，全部取自 train） | 200 | **100%** | 0 | **0.8321** | **0.5395** | **0.0852** | 0.9384 | **4.09 s** | 311,084（prompt 292,091 + 生成 18,993） |
| 本地 Qwen3-0.6B zero-shot（n=60，batch 8） | 60 | **100%**（解析器修复后） | 0 | **0.4068** | **0.1167** | **0.0000** | 0.6074 | **5.32 s/条** | 63,795（prompt 54,683 + 生成 9,112） |
| LoRA SFT（Qwen3-0.6B，1 epoch × 3,500 条，**11-18 重训**） | 200 | **100%** | 0 | **0.9000** | **0.6971** | **0.1850** | **0.7862** | **5.43 s/条** | —（本地推理，无 API 费用；adapter 9.2 MB） |

**能直接下的结论（都有 JSON 支撑）**：

1. **格式不是瓶颈**：约束足够强的 prompt + 解析兜底 → **200 条 JSON 合法率 100%**、0 空回复、0 修复。
2. **格式合法 ≠ 字段合法**：schema 不合规的角色 **zero 只有 4 个 / few 3 个**（第一版 prompt 里角色用 `/`
   分隔、和角色名自带的斜杠撞车时，这个数字是 84 个——见 §7 第 21 条）→ 即便如此，
   生产系统仍然必须有 schema 校验（L5 的 `_validate()` 就是干这个）。
3. **生成式偏移漂移真实存在**：论元不在原文 **zero 6 条 / few 6 条**，触发词不在原文 **各 0 条** →
   这就是为什么必须 `text.find()` 对齐而不是相信模型给的坐标。
4. **few-shot 的收益在事件级**：event F1 0.0402 → 0.0905（**+5.0pp**），trigger 0.7789 → 0.8291（+5.0pp），
   argument 0.5246 → 0.5347；但 **prompt token 从 169,891 涨到 292,091（+72%）**，总 token +62%
   （191,578 → 311,084）——示例是"免费的领域适配"，但成本要算进选型。
5. **成本要进选型表**：平均 3.5~3.6 s/条、约 0.96k~1.56k token/条；日更 1 万条 ≈ 9.6~15.6M token/天。
6. **同一个 0.6B，微调后从「不可用」变成「最强」**：zero-shot argument **0.1129** → LoRA SFT **0.6971**（n=200），
   而且 LoRA 只训练 **0.38%** 参数（2.29M/598M）、1 epoch × 3,499 条、**2,327 s**、峰值 **4.0 GiB**。
   这条对比（零样本 vs 微调）比任何「模型大小」的讨论都有说服力：**任务格式和标注口径是学出来的**。
7. **生成式 vs 判别式的分工**：LoRA 论元更强（0.6971 vs 0.6418），但 event_exact 更低（0.1850 vs 0.2268）
   —— **生成式召回好、边界糙；序列标注边界准、召回受标签空间限制**。生产上常见组合是
   「生成式抽候选 + 判别式/规则修边界」。
8. **本地 0.6B zero-shot 在结构化抽取上不可用**：n=60 上 argument F1 **0.1129**（低于规则 0.1740）、
   event_exact **0.0000**、type_macro 0.6074 —— 所以 L3 要么用 API，要么上 LoRA 微调（L4）。
9. **解析器写得好不好，指标差 8 个点**：本地模型 60 条里有 **18 条**吐出「少一个右括号」的畸形 JSON，
   栈式括号修复后 JSON 合法率 **70% → 100%**，trigger F1 **0.3299 → 0.4174**、argument **0.0698 → 0.1129**。
   同一份模型输出、只改解析器就差 8 个点 —— **容错解析不是锦上添花，是链路的一部分**。

### 4.6 非法 BIO 序列（linear vs crf，本周"看得见"的收益）

| | 含非法序列的句子数 | 非法开头 | 非法转移 | 每条句子平均非法数 |
|---|---|---|---|---|
| **金标自身（dev，地板值，`eval/check_bio_gold.py`）** | **18 / 930 = 1.9%** | 0 | 18 | **0.019** |
| 金标自身（train） | 94 / 5,747 = 1.6% | 0 | 94 | 0.016 |
| BERT + Linear（`bert_linear_256`） | **623 / 930 = 67.0%** | 0 | **1,516** | **1.63** |
| BERT + CRF（软约束，`bert_crf_256`） | **581 / 930 = 62.5%** | 0 | **1,242** | **1.34** |
| BiLSTM-CRF（无预训练，`max_len=128`） | **454 / 930 = 48.8%** | **50** | 660 | **0.763** |
| BERT + CRF（`bert_crf_256_hard`，解码期硬约束） | 69 / 930 = 7.4% | 0 | **token 级 0**；字符级口径仍报 155（**100% 由 span 内空格造成**） | — |
| 随机 emission 对照（`crf.py` 自检） | — | — | — | **12.2 处/条**（无约束）→ **0**（硬约束） |

**这张表里最重要的不是"CRF 降了多少"，而是"该看哪个指标"**：

- CRF 把**非法转移数**降了 **18%**（1,516 → 1,242，每句 1.63 → 1.34），
  但「**含非法句占比**」只从 67.0% 降到 62.5% ——因为一句平均 175 个 token、有 174 个转移位点，
  只要**任意一个** span 的开头吐成 `I-` 而不是 `B-`，整句就算"含非法序列"。
- 所以「含非法句占比」在长序列上区分度极差，**能反映 CRF 作用的指标是"非法转移数 / 每句平均非法数"**。
  选错指标会把机制掩盖掉（这类"指标选错导致结论反转"的坑，在往期项目里也踩过）。
- 而且非法率有 **1.9% 的不可消除地板**：金标自己就有 18 处非法转移（论元重叠、BIO 表达不了）。
  **任何「非法率」都不能和 0 比，只能和地板值比。**
- **「硬约束后还报 155 处」已闭环**：token 级严格 **0 处**（机制正确）；字符级口径仍报 155 处 / 69 句，
  逐条核对发现 **100% 的前一字符是空白** —— 原文里的空格（如「9 月 8日」）不产生 token、被强制标 `O`，
  跨空格的 span 在字符级 BIO 上看起来就像 `O → I-`。**这是字符级统计口径的产物，不是模型问题。**
  PPT 金句：**同一件事换一种统计粒度，结论就变了** —— 这正是 §4.6 开头「该看哪个指标」的加强版。

> 统计口径在 `common/event_data.py: illegal_bio_stats()`：
> `illegal_seq_rate`（多少条**句子**里出现非法 BIO，PPT 最直观）与
> `illegal_per_seq`（平均每条几处，看严重程度）分开报，不混用。

### 4.9 本周最强的一格：CRF 硬约束解码（不重训，论元 +7.5pp）

同一个 `bert_crf_256.pt`，**只是把解码期的非法转移 mask 成 `-1e4` 后重跑维特比**：

| | 软约束（默认） | **硬约束（解码期）** | Δ |
|---|---|---|---|
| trigger F1 | 0.8320 | **0.8464** | +1.44pp |
| argument F1 | 0.5815 | **0.6566** | **+7.51pp** |
| event_exact F1 | 0.1697 | **0.2177** | **+4.80pp** |
| 非法转移（按评测脚本口径） | 1,242 | **155**（−87.5%） | — |
| 含非法句占比 | 62.5% | **7.4%** | −55.1pp |
| 训练成本 | — | **0（复用 ckpt，decode 90 s）** | — |

**为什么"只改解码"能涨 7.5 个点**：维特比是在**全局路径分数**上取最优。软约束下，模型完全可能选择一条
"总分略高但局部非法"的路径——比如把 `I-回购股份数量` 接在 `O` 后面。这种路径在 BIO 语义上是坏路径，
解码器一旦被禁止走它，就只能重新在合法路径里找最优解；而合法路径算出来的 span 边界恰好更接近金标。
**结论：非法序列不只是"输出难看"，它本身就是 Span 边界错误的一种表现形式。**

**配套的坑（必须讲）**：硬约束一开始「假生效」——eval 报的非法数和软约束**一模一样（1,242 处）**。
根因是 `crf.py` 把约束矩阵注册成 **buffer（`persistent=True`）**，会跟着 checkpoint 一起存；
checkpoint 是软约束训出来的（buffer 全 True），于是"先装硬约束 → `load_state_dict` 又把它覆盖回全 True",
一条约束都没生效。抓法是 eval 里那句防御性检查「已装载：禁止 **0** 个非法转移对」；修法见 §7 第 28 条。
**这是序列标注里最典型的假象：以为加了约束，其实状态被 checkpoint 静默覆盖了。**

1. **微调过的生成式模型才是最强**：LoRA 论元 **0.6971** 高于硬约束 BERT（0.6418，**+5.5pp**）、

## 5. Bad Case 分析

> 数字口径：`argument F1` 与 `event_exact F1` 主要丢分点来自下面四类。
> 具体 bad case 计数在 `NOTES_discriminative.md` / `NOTES_llm.md`（实验跑完后补齐）。

### 5.1 触发词歧义：「质押」vs「解除质押」

```
文本：傅宇晨解除部分股份质押，累计质押比例为39.55%
金标：解除质押（trigger=解除部分股份质押）
```

- 规则：最长优先能救大部分，但词表里没有的写法就判错 → `wrong_type` 占规则错误的 **15.2%**。
- 模型：联合标签体系里 `TRG:质押` 与 `TRG:解除质押` 是两个标签，靠上下文区分；
  两段式则退化为 13 分类问题，实测同样会混（`per_type` 里这两类 F1 最低）。
- **这就是事件抽取比 NER 难的地方**：实体类型不会因为"多了一个字"就变成另一个类型，事件类型会。

### 5.2 论元角色串味：金额/日期填错角色

```
金标：回购股份数量=380.5万  交易金额=94.56万港元
错误：回购股份数量=94.56万港元  交易金额=380.5万    ← 数字都对，角色全串
```

- 规则系统头号错误就是它：`arg_spurious` **55.6%**（规则分不清哪个数字属于哪个角色）。
- 模型：`argument` F1 的主要损失也来自这里；LLM 同样会串（per_role 里「披露时间」「交易金额」
  「每股交易价格」的 FP 最多）。
- 改进方向：角色-数值类型的**约束**（金额角色只接受带"元"的片段、比例角色只接受带"%"的片段）。

### 5.3 边界偏移：触发词/论元的首尾多一个字

```
金标：回购方=众安集团         预测：回购方=众安集团10月15日耗资
金标：trigger=回购           预测：trigger=回购股份
```

- `trigger` 与 `argument` 都是**文本完全相等**才算 TP，多一个字就是 FP+FN 双输。
- 序列标注天然对齐字符边界，但仍会被"词边界不等于 span 边界"困扰
  （`回购股份` 既可能是触发词也可能含论元）。
- 数据本身的瑕疵：**trigger span 与某论元 span 完全相同**的情况 train 238 / dev 38 个事件（约 4.1%），
  BIO 标注必然冲突 → 本项目取「触发词优先」并在 `span_conflicts` 里记账。

### 5.4 枚举型论元抽不出来（数据层的天花板）

```
金标：公司上市 → 环节=筹备上市
原文：「理想汽车拟将美国IPO定价在招股区间顶端…」← 原文里根本没有"筹备上市"四个字
```

- 这类"归一化取值"的论元无法用 span 定位，转换阶段被丢弃：train 丢 347 个、dev 丢 56 个，
  **占论元 1.36%/1.34%** → 这就是为什么论元定位率是 98.6% 而不是 100%。
- 影响：这是评测的**理论上限损失**，报告里必须写清分母与丢弃量；模型再强也抽不出原文没有的字。
- 工程解法：枚举角色靠 schema 枚举补 + `enum_mismatch` → `needs_review`（L5 已实现）。

### 5.5 生成式漏抽与幻觉（L3/L4 特有）

| 现象 | 实测 | 后果 |
|---|---|---|
| 空回复 | API zero/few 各 0 条（开思考的推理模型会大量空回复，已用 `thinking: disabled` 规避） | 记为 `events: []`，分母不变 |
| 触发词不在原文 | zero 0 条 / few 0 条 | `text.find()` 返回 -1，trigger 必错 |
| 论元不在原文 | zero 6 条 / few 6 条 | 幻觉论元，算 FP |
| 角色名自造 | zero 4 个 / few 3 个（第一版 prompt 因分隔符撞车高达 84 个，见 §7 第 21 条） | 需 schema 校验兜住 |
| 漏抽（少给论元） | 见 `argument` 召回的缺口 | 直接拉低 argument F1 |

### 5.6 论元口径不一致：数量类论元"全错"但不是"没抽到"

这是本项目最值得讲的一个 Bad Case（详见 `outputs/llm/badcase_unit_denominator.md`）：

```
金标：回购股份数量 = 9.18万
模型：回购股份数量 = 9.18万股
```

- 金标**去掉了单位**（只留「9.18万」），模型按自然语言习惯写成「9.18万股」；
  在"文本完全相等"的严格口径下，**整条论元算错**（FP+FN 双输）。
- 铁证：200 条抽样里三个数量类角色（`回购股份数量 / 质押股票/股份数量 / 交易股票/股份数量`）
  金标共 **75 次**；**角色名对得上 32/32、25/25、17/18，但"文本完全相等"只有 0/75**——
  全部只差一个「股」。模型输出是原文逐字片段，**错在金标把单位截掉了**。
- 后果：这三个角色 F1 = **0.0000**，把整体 argument F1 明显拉低（0.5246）。
- 上限分析（只做分析、不进正式表）：gold/pred 同时把数量类去尾「股」再评，
  argument F1 **0.5246 → 0.5953（+7.1 点）**、event 0.0402 → 0.0553 ——
  **这 7 个点全是标注口径，不是模型能力**。正式指标仍用 strict，明细见 `outputs/llm/badcase_unit_denominator.md`。
- 这**不是模型能力问题，是标注规范问题**：同一个日期金标可能标成「回购完成时间」、
  模型答成「披露时间」，也是角色口径分歧。
- 工程上只有三条路（**评测侧不能偷偷放水，那等于改分**）：
  ① 统一标注口径（金标补单位）；② 评测侧做规范化（单位/同义角色映射），但**必须声明口径**；
  ③ 业务侧重新定义论元 schema。

## 6. 优化方向

### 数据层面
- **补真实长篇公告**：本数据集是 2019–2020 年标题式短句为主（篇长 p50 506 字），
  与今天的公告版式有差距；产品化要补真实样本。
- **同串多次出现的 span 标注**：30.6% 的 span 字符在句内出现多次、取首次出现，
  这是本数据集精度上限；要彻底解决需要"第 N 次出现"的标注。
- **多事件句**：`extract` 只保留单事件句（排除了 4.6%），多事件要靠 `detect` + 篇章合并（L5 已做）。

### 模型层面
- **span-based 抽取**（如 Biaffine / GlobalPointer）：直接预测起止，避免 BIO 边界误差传播。
- **角色-数值类型约束**：金额角色只接受数字+单位、比例角色只接受百分数，压掉"角色串味"。
- **两段式第三段上 CRF**：目前刻意用线性头，长尾类型可以试试。
- **换更大/更新的中文预训练（roberta-wwm-ext、金融域继续预训练）**。

### 训练策略
- 长尾类型（被约谈 53 条、股东增持 162 条）做**类型加权重采样**或 focal loss。
- 联合模型里对长尾角色做**标签平滑 / 损失加权**。
- SFT 从 1 epoch 增到 3 epoch（并保留内层验证选点），当前只是教学规模。

### 工程部署
- 两段式 13 个专家模型用**ONNX / int8 量化**压缩，或蒸馏成一个模型。
- 推理侧批量化 + 动态 padding（本项目已用动态 padding，还能再上 `torch.compile`）。
- `needs_review` 队列接人工审核平台：按"每 100 条能捞回多少错"衡量 ROI。

| 32 | **截断就是召回上限，容易被忽略** | `max_len=256` 时 dev 有 **13.1%** 句子被截断（`max_len=128` 时 **68.7%**），尾部 span 必丢 | 报告里必须写截断率；用动态 padding 后把 `max_len` 提到 384 几乎不额外花时间（算真实长度），可作为学生练习 |
| 33 | **硬约束"假生效"：以为加了约束，实际一条没加** | 约束矩阵是 CRF 的 **buffer（`persistent=True`）**，跟着 checkpoint 存；checkpoint 是软约束训的（buffer 全 True），`load_state_dict` 会在"装硬约束"之后把它**覆盖回全 True** | 抓法：eval 里打印「已装载：禁止 N 个非法转移对、M 个非法起始标签」，N=0 就是没生效；修法：**load 完再装一遍约束**，并 `if n_forbidden == 0: raise RuntimeError` 断言。修好后论元 F1 才从 0.5815 变成 **0.6566** |
| 34 | **规则兜底上线反而掉点** | 第一版判据用「区间重叠率 ≥0.5」→ 给 79 个论元回填，argument F1 **0.5815 → 0.5800（−0.15pp）**：触发词「辞去」与论元「辞职」**同义不同形**，回填错文本只增假阳性 | 改成「**文本完全相等率 ≥0.5 且样本 ≥3**」→ 只学到 1 条规则（`高管变动.变动类型`，236/260 = 90.8%），回填 31 个论元 → arg **0.5815 → 0.5831**、event **0.1697 → 0.1763**。**规则要先验证再上线，判据错会负收益** |
| 35 | **小模型的 JSON 畸形被当成"模型不会"** | 本地 Qwen3-0.6B 60 条里 **18 条**少了 events 列表的 `]`（`...}]}}`），旧解析器直接判失败 | 栈式括号修复后 JSON 合法率 **70% → 100%**、trigger F1 **0.3299 → 0.4174**、argument **0.0698 → 0.1129**。**同一份模型输出，解析器差 8 个点**；`--from_raw` 可只重解析不重跑模型 |
| 36 | **"temperature=0 就一定可复现"是错的** | 服务端 MoE 路由/并行归约的非确定性：同一批 prompt 重跑，trigger F1 在 **0.78~0.81** 间波动 | 线上必须**固定模型版本 + 记录评测批次**；做对比实验时同一条结论要看两次跑是否稳定，不要把 ±0.02 的波动当成"改了 prompt 变好了" |
| 37 | **训练预算被切碎，模型再好也训不出来** | 两段式要训 16 个模型，13 个专家每个每 epoch 只有 **3~31 步**（3 epoch 才 90 步量级），而联合模型有 486 步 | 端到端 0.369 远低于联合 0.582 —— 诊断显示检测器 0.7740、类型 0.9452 都正常，**损失全在欠训练的论元专家上**。教训：**拆流水线前先算训练步数预算**，不是拆得越细越好 |
| 38 | **类型条件专家「能跑、训练 loss 也降」，但推理全错（F1=0）** | `span_to_char_tags(typed=True)` 的刷标签分支写错：`etype = TRIGGER_TAG if typed else ...` → **typed 模式下所有论元都被刷成 `TRG`**，专家学成"到处是触发词" | 症状很好认：预测的 trigger 是**随机一个汉字**、论元全空（如金标 `IPO`+4 论元 → 预测 `trigger="甚"`、`args=[]`）。修法：`etype = role if typed else f"{ARG_PREFIX}{role}"`。**教训：标签刷错不会报错、loss 也照降，只有逐条看预测才抓得到**——"跑通"和"跑对"是两件事 |
| 39 | **切句的字符偏移会「悄悄」漂移，篇章级 span 全部指错位置** | `split_sentences()` 用 `start += len(seg)` 累加偏移，而正则 `[^。！？；\n]+[。！？；\n]?` 要求至少一个非标点字符 → **连续标点、空行整段不匹配、偏移漏加**，逐段向左漂移（dev_docs 985 篇里 798 篇漂移 = 81%，最大 1249 字；demo 产物 57 个 span 有 33 个对不上原文） | 切分时**只记区间 `(start, end)`**，片段文本一律 `text[s:e]` 切片（保证 `text[off:off+len(seg)] == seg`）；并在生成端到端产物后加一条全量自检：每个 span 都必须 `text[start:end] == span.text` |

**目录设计的三条规矩**（改目录时请一起改）：

1. **每个方法一个文件夹**，方法之间**互不 import 训练代码**；要共享的（数据层/模型结构/评测/日志）放 `common/`。
   `models.py` 单独存在的原因：`bert/train.py`、`bilstm_crf/train.py`、`bert_pipeline/train.py` 同名，
   同时放进 sys.path 会撞名，而 `service/` 需要同时用 bert 的编码器和 bert_pipeline 的分类头。
2. **每个方法脚本开头统一**：`ROOT = Path(__file__).resolve().parents[1]` + `sys.path.insert(0, str(ROOT / "common"))`。
3. `outputs/` 下**每个数字都能反查到一条命令**：指标 JSON 里带 `meta`（超参/训练时长/延迟/设备），
   训练日志带 `argv`/`env`/逐步曲线，`run_experiments.py` 记录完整命令与退出码。
   这是"图注和实际跑的参数不会打架"的保证。
