# RESUME_GUIDE.md — 求职简历指导

> **一句话结论**：这个项目能写进简历的**硬货**有三类——
> ① 一条完整的「数据 → 六层方法 → 统一评测 → 系统化」链路；
> ② 一串**可复现的真实数字**（规则基线 0.17、API 论元 0.52、CRF 非法转移 12.2→0…）；
> ③ 一批**别人答不上来的工程细节**（doc id 不唯一、生成式 offset 不可信、loss masking 显存账）。
>
> **不要**写"用 BERT 做了事件抽取"——那是课程作业；要写"六层方案在同一批数据上量化对比，
> 并给出可上线的混合架构"，这才是项目。

### 1.2 方法数量

**六层 / 10 条可评测链路 + 1 个系统组合**：规则（L0）；BiLSTM-Linear、BiLSTM-CRF（L1）；
BERT-Linear、BERT-CRF（L2 联合 149 标签）、两段式流水线（检测 + 类型 13 分类 + 13 个类型条件专家）；
API zero-shot、API few-shot、本地 Qwen3-0.6B zero-shot（L3）；LoRA SFT（L4）；
最后把这套能力串成「切句→抽取→校验→兜底→复核→篇章合并」的服务（L5）。
另有 **3 组消融**（`max_len` 128/256、BERT 4 层/12 层、CRF 硬约束）。

## 2. 项目名称怎么写

| 写法 | 质量 | 原因 |
|---|---|---|
| "用 BERT 做了事件抽取" | ❌ 差 | 没有场景、没有方法对比、没有数字，像课程作业标题 |
| "金融公告事件抽取（信息抽取项目）" | ⚠ 一般 | 有场景，但看不出你做了什么、做到了什么水平 |

## 3. 按岗位方向写法（完整简历片段，可直接粘）

### 3.1 算法工程师 / NLP 方向

> **金融公告事件抽取（信息抽取）：六层方案对比 + 混合抽取架构**
>
> - 基于 DuEE-Fin（13 类事件 × 61 个角色，句子级单事件 train 5,747 / dev 930）实现**同一评测口径下
>   10 条链路**的横向对比：规则基线、字符级 BiLSTM-CRF、BERT+Linear/CRF 联合标注（149 标签）、
>   两段式流水线（检测 + 13 分类 + 13 个类型条件论元专家）、LLM zero/few-shot、LoRA SFT；
>   自建统一评测函数输出 **trigger / argument / event_exact 三级 F1 + type_macro + per_type/per_role**。
> - **量化了"规则能判类型、填不满槽位"**：规则基线 trigger F1 0.6168、type_macro 0.8118，但
>   argument F1 仅 **0.1740**（错误 55.6% 是"金额/日期填错角色"），据此确定模型要补的能力边界。
> - 三台阶定位（同一 dev 930）：规则 **0.1740** → 字符级 BiLSTM-CRF **0.4634（+28.9pp）** → BERT+CRF **0.5815（+11.8pp）**，
>   把「有建模」和「有预训练」的收益分开量化；BiLSTM 只有 **1.31M** 参数（BERT 的 1/78），
>   说明触发词不吃预训练、**论元才吃**。
> - 判别式主线：BERT+Linear（联合 149 标签）trigger/argument/event F1 **0.8293 / 0.5630 / 0.1564**；
>   换 CRF 解码后 **0.8320 / 0.5815 / 0.1697**（论元 +1.85pp、事件 +1.33pp），
>   11/18 重跑耗时 **637s → 2742s**、推理 **3.3×**（12.26→40.92 ms/句）——用这组数字说明"精度 vs 延迟"的取舍。
>   ⚠ **训练倍率 5.9× 的口径**：取自**首跑**（11/16，无并行任务）**531s → 3112s**。
>   11/18 重跑时同机 CPU 上有 BiLSTM 并行训练、两条耗时被争用影响（637s / 2742s 一升一降），
>   **不能用来重算倍率**；要引用"CRF 慢多少倍"请用首跑那两个数。
> - 联合 vs 两段式：两段式把标签空间从 **149** 缩到 **11~19**（单类型专家），并做**类型给金标的上界分析**
>   隔离"类型错"与"论元抽不准"两种损失来源；两段式 15 个模型只保留 4 层 BERT（102.4M→45.7M/个）控显存。
> - 手写 Linear-chain **CRF**（前向 logZ / 维特比 / start+转移硬约束）：与暴力枚举全路径对拍误差
>   **0.00e+00**；随机 emission 下每条序列 **12.2 处**非法转移，硬约束后 **严格 0**；并实证
>   "只加转移约束时非法开头仍有 42%"——纠正了"CRF 天然保证合法序列"的常见误解。
> - 非法 BIO 定量：Linear 非法转移 **1,516 处**（每句 1.63）→ CRF **1,242 处**（1.34，−18%）；
>   同时指出「含非法句占比」（67.0%→62.5%）在长序列上区分度极差，**应看非法转移数**，
>   且金标自身就有 **1.9%** 的非法地板（`check_bio_gold.py` 实测 18 处）——**非法率不能与 0 比**。
> - **L4 最亮的一格**：同一个 Qwen3-0.6B，零样本 argument **0.1129** → **LoRA SFT 0.6971**（n=200），
>   反超最强判别式（硬约束 BERT 0.6418，**+5.5pp**）、远超 API few-shot（0.5347，+16pp）；
>   只训 **0.38%** 参数、1 epoch × 3,499 条、**2,327 s**、峰值 **4.0 GiB**、adapter **9.2 MB**。
>   但 event_exact（0.1850）仍低于判别式（0.2268）→ **生成式召回强、边界弱**，两条路线互补。
> - **本项最强结论（零成本提点）**：同一个 CRF checkpoint，**只把解码期非法转移 mask 掉**（不重训、
>   decode 90 s），论元 F1 **0.5815 → 0.6566（+7.51pp）**、事件 F1 **0.1697 → 0.2177（+4.80pp）** ——
>   证明「非法解码本身在破坏 span 边界」，约束不是锦上添花而是准确率的一部分。
> - **排查过一个「假生效」深坑**：硬约束初版报的非法数与软约束一模一样（1,242 处）——因为约束矩阵是
>   CRF 的 **buffer（persistent=True）**，`load_state_dict` 把刚装上的硬约束覆盖回软约束；用
>   「已装载：禁止 N 个非法转移对」的防御性检查（N=0 即未生效）抓出，改成 load 后再装 + 断言。
> - LLM 链路：固定 n=200 嵌套子集（seed=42）评测，zero-shot 三级 F1 **0.7789 / 0.5246 / 0.0402**、
>   JSON 合法率 **100%**；few-shot（6 例取自 train）事件级 **0.0905**、token 成本 +72%；据此提出
>   "格式合法 ≠ 字段合法"（schema 不合规角色 zero 4 个 / few 3 个；第一版 prompt 曾高达 84 个），必须配 schema 校验。
> - 三台阶 + 一跳变：规则 0.1740 → BiLSTM-CRF 0.4634 → BERT+CRF 0.5815 → **LoRA SFT 0.6971（n=200）**；
>   同一个 0.6B 模型零样本只有 0.1129，**微调后反超全部判别式** —— 说明小模型缺的是任务格式与标注口径，不是参数量。
> - 本地 0.6B zero-shot（n=60）实测 argument **0.1129**、event **0.0000** → **零样本小模型做结构化抽取不可用**；
>   但把 JSON 解析器从「直接 json.loads」改成「栈式括号修复」后，合法率 **70%→100%**、trigger **0.3299→0.4174**
>   ——同一份模型输出，**解析器差 8 个点**。
> - 技术栈：PyTorch、HuggingFace Transformers、手写 CRF、peft(LoRA)、OpenAI 兼容 API。

### 3.2 后端 / AI 应用工程化方向

> **金融公告事件抽取服务（抽取 + 校验 + 人工复核的混合架构）**
>
> - 把"模型指标"变成"可上线系统"：公告全文 → 中文切句（保留字符偏移）→ 逐句抽取 → **schema 校验**
>   （角色必须属于该事件类型）→ **span 校验**（论元必须能在原文找到，防幻觉）→ **正则兜底**
>   （模型漏掉的金额/日期/比例/股数用正则补，标 `source=regex`）→ **置信度门控**（低置信 /
>   缺核心角色 / 枚举不合法 → `needs_review` 人工复核）→ **篇章合并**（同类型事件合成事件流，
>   记 `sent_ids` 可溯源）。
> - 两种可切换后端：单模型联合抽取（1 次前向、延迟低）与两段式（15 个模型、精度更高）；
>   13 个类型专家**依次训练、训完即释放**，把 8GB 显卡上的峰值显存压到可跑。
> - 统一评测工程：所有方法只产出同一种预测 JSONL（`id + sent_id + events`），指标只能由
>   `common/evaluate_events.py` 这一个函数算；预测里解析失败的行**保留空结果**（不删分母），
>   并额外把全量预测**投影到固定 n=200 子集**，解决"判别式 930 条 vs LLM 200 条不可比"的问题。
> - 成本意识：API 链路实测 **3.53~3.62 s/条、0.96k~1.56k token/条**（日更 1 万条≈9.6~15.6M token/天），
>   BERT 链路 **12.26 ms/句（Linear）/ 40.92 ms/句（CRF）**，规则链路 **0.72 ms/句**；
>   据此给出"规则兜底 + 模型抽结构 + 人审 20%"的分层方案。
> - 可运维性：提供「不重训的复评/改法」三件套——`bert/evaluate.py`（checkpoint 复评）、
>   `bert/evaluate_hard_constraint.py`（解码期硬约束，**论元 +7.5pp、零训练成本**）、
>   `postprocess_trigger_copy.py`（规则回填，argument 0.5815→0.5831）；并把置信度从「概率连乘」
>   改成「按 token 平均概率」（否则 0.93^68≈0.007，所有样本都被误判为低置信）。
> - 规则兜底的取舍经验：回填判据先用「区间重叠率」→ 回填 79 个论元反而 **−0.15pp**（「辞去」vs「辞职」
>   同义不同形）；改成「文本完全相等率」→ 只回填 31 个论元、**+0.16pp**。**规则只能补模型系统性漏的那一格。**
> - 数据工程：原始镜像的 offset 实为 `text.find()` 首次出现回填（审计 52,395 个 span **0 例**与 find
>   不一致），因此**重建全部 span** 并逐行校验（45,143 个 span **0 错误**）；发现 dev 检测集与训练集
>   文本重复 **9.2%**，产出 clean 版评测集（4,815 条）双口径上报。

## 4. 按经验层级写法

### 4.1 应届 / 转行第一份工作

> **金融公告事件抽取（个人项目 / 课程项目）**
>
> 用 DuEE-Fin（13 类事件，句子级 train 5,747 / dev 930）把信息抽取的六层做法都实现了一遍：
> 规则基线 → BiLSTM-CRF → BERT 联合序列标注（149 标签）→ 两段式（检测+类型+类型条件论元）→
> LLM 提示 → LoRA 微调，最后串成一个能抽整篇公告的事件流服务。
> 印象最深的三个点：① 规则能把类型判到 0.81，但论元只有 0.17（金额/日期总填错角色），这让我第一次
> 直观看到"为什么需要序列标注模型"；② 生成式模型给出的字符下标不可靠，改成"只让模型抄原文片段、
> 程序用 find 对齐"后才稳定；③ 评测必须只有一把尺子——我第一版因为没带句子 id，同文档多句预测互相
> 覆盖，gold 对 gold 只有 0.93 F1，加了 `id|sent_id` 才是 1.0。
> 技术栈：PyTorch、Transformers、手写 CRF、peft/LoRA、OpenAI 兼容 API。

### 4.2 1~3 年经验

> - 主导金融公告事件抽取链路：13 类事件 × 61 角色，句子级 train 5,747 / dev 930，实现规则 /
>   BiLSTM-CRF / BERT 联合与两段式 / LLM zero-few-shot / LoRA SFT 共 10 条链路并统一评测口径。
> - **定位瓶颈**：规则基线 trigger F1 0.6168 / type_macro 0.8118，但 argument F1 仅 0.1740，
>   错误 55.6% 为"数值填错角色"；据此把工作重心从"判类型"转到"类型条件论元抽取"，两段式把标签空间
>   从 149 压到 11~19，并用"类型给金标"的上界分析区分误差来源。
> - **手写 CRF 并做实证**：前向 logZ / 维特比与暴力枚举对拍误差 0.00e+00；随机 emission 每条 12.2 处
>   非法转移 → 硬约束后严格 0；实证「只加转移约束时非法开头仍 42%」，据此在训练里加 start 约束。
>   线上对照：Linear 非法转移 1,516 处 → CRF 1,242 处（每句 1.63→1.34），且发现金标自身有 1.9% 非法地板。
> - **找到并修复一个「静默失效」问题**：CRF 的约束矩阵是 `persistent` buffer，会在
>   `load_state_dict` 时被 checkpoint 覆盖 → 硬约束等于没加；用「已装载：禁止 N 个非法转移对」检查抓出，
>   修好后论元 F1 从 0.5815 提升到 **0.6566（+7.5pp）**、训练成本 0。
> - **评测体系治理**：统一预测格式（`id|sent_id` + events）、统一评测函数（三级 F1 + macro + per_role）、
>   固定 n=200 嵌套子集做跨链路可比，并把解析失败样本保留在分母里（避免指标虚高）。
> - **指标选择治理**：发现规则基线 type_macro F1（0.8118）反而高于 BERT（0.7654），据此明确
>   "不能只看类型指标"；非法 BIO 也改用"非法转移数/每句"而非"含非法句占比"，避免结论被指标掩盖。
> - **系统化落地**：切句 → 逐句抽取 → schema/span 双校验 → 正则兜底 → 置信度门控 → 篇章事件流合并；
>   8GB 显卡上 13 个类型专家按"训完即释放 + 4 层截断"跑通。

### 4.3 3 年以上 / 资深

> - **技术选型决策**：面对"判别式 vs 生成式"的路线选择，用同一批样本、同一评测函数做了 10 条链路的
>   量化对比（规则 / BiLSTM-CRF / BERT 联合 / 两段式 / LLM zero-few-shot / LoRA SFT / 混合系统），
>   并给出结论：**结构化槽位以序列标注为主、长尾/新类型用 LLM 提示兜、数值类字段用正则兜底**，
>   而不是单一押注某个模型。
> - **误差预算管理**：把端到端损失拆成"检测漏抽 / 类型判错 / 论元抽取"三段分别量化（检测集单独建
>   985 篇篇章级评测 + 类型 oracle 上界），使每个优化动作都能对应到具体环节的收益，而非整体 F1 波动。
> - **架构取舍的实证**：两段式（16 个模型）端到端只有 0.369 论元，远低于联合模型 0.582——诊断后定位
>   不是方法问题而是**训练预算被切碎**（13 个专家每 epoch 仅 3~31 步 vs 联合 486 步），
>   据此得出「小团队/小显卡优先联合模型」的工程结论。
> - **性价比决策**：用同预算对照给出 CRF 的收益/代价曲线（论元 +1.9pp、事件 +1.3pp vs 训练 5.9×、
>   推理 3.3×），并据此区分「离线批处理用 CRF、在线高吞吐用 Linear」的部署口径。
> - **零成本提点的挖掘**：在不动模型、不改训练的前提下，系统性尝试解码约束/后处理/解析器三条改法，
>   最终拿到 decode 90 s 换 **论元 +7.5pp、事件 +4.8pp** 的最大性价比改进，并明确其机制
>   （非法解码破坏 span 边界），而不是当成调参玄学。
> - **可上线性设计**：确立"模型抽结构 + 规则补数字 + schema/span 双校验 + 低置信转人工"的混合架构，
>   用 `source=model|regex` 与 `needs_review` 原因码把系统行为变成可解释、可审计、可回滚的；
>   成本上算清 API 链路 3.5~3.6 s/条、9.6~15.6M token/天与规则链路 0.72 ms/句的量级差异。
> - **评测治理**：主导统一评测规范（唯一评测函数、`id|sent_id` 对齐、不删失败样本、固定嵌套子集、
>   clean 版去 9.2% 泄漏双口径），从流程上杜绝"谁的脚本谁自己算指标"导致的口径漂移。

## 6. 面试常见追问（15 题）

### Q1：CRF 为什么能把非法序列降下来，却降不到 0？怎么才能到 0？
CRF 的转移矩阵是**学出来的参数**，训练只是让"非法转移"分数变低，并没有禁止它；而且转移矩阵
只管第 2 个 token 往后，**"第一个 token 就是 `I-x`"靠转移矩阵根本管不到**。
本项目实证：只加转移约束时非法开头仍有 **42%**，必须再单独加 `start_constraint`；
要彻底归零，就得把非法转移的分数显式置 `-1e4`（解码期硬约束），而这已经不是"学"而是"约束"
（`-inf` 在反传时容易 NaN，所以用大负数）。

更关键的是**这个问题的量级和「正确指标」以及「它值多少钱」**：同样的 CRF checkpoint，只把解码期非法
转移 mask 掉（不重训），论元 F1 **0.5815→0.6566（+7.5pp）**、事件 **0.1697→0.2177（+4.8pp）**——
说明**非法解码本身在破坏 span 边界**，约束不是「输出好看」，是准确率的一部分。

⭐ 还有一个非常值得讲的细节：硬约束修好后，**token 级非法转移严格 0**，但按字符级口径仍报 **155 处**；
逐条核对发现 155 处 **100% 的前一字符是空白**——空格不产生 token、被强制标 `O`，跨空格的 span
（如「9 月 8日」）在字符级 BIO 上就像 `O→I-`。**同一个模型，换一种统计粒度结论就变了**，
这也是我后来坚持「报指标必须写清口径」的原因。

BERT+Linear 有 **1,516 处**非法转移（每句 1.63），
CRF 降到 **1,242 处**（1.34，−18%）；但"含非法句占比"只从 67.0% 降到 62.5%——因为一句平均 175 个
token、174 个转移位点，任意一处出错整句就算。而且**金标自身就有 18 处（1.9%）非法转移**
（论元重叠，BIO 表达不了），所以非法率有不可消除的地板，**只能和地板值比，不能和 0 比**。

### Q2：联合抽取（149 标签）和两段式流水线，你会选哪个？
看瓶颈在"类型"还是"论元"。
- 联合：1 个模型、1 次前向、无误差累积，但 149 个标签里长尾角色样本被摊薄（很多角色训练样本不到 100）；
- 两段式：标签空间缩到 11~19、单标签样本密度高一个数量级，论元边界通常更准；代价是 15 个模型、
  3 倍延迟、**类型判错则论元全错**。
本项目的做法是**两个都实测**，并加一条"类型给金标"的上界，用差值判断类型错背了多少锅。
工程上结论是：类型分布稳定、延迟敏感 → 联合；类型只有十几类且论元质量要求高 → 两段式。

### Q3：BERT 中文序列标注，子词对齐具体怎么做？为什么非首子词要设 -100？
中文 BERT 也是 WordPiece：生僻字会变 `[UNK]`、数字/英文会被切成 `8` `##-` 之类。
做法：`tokenizer(list(text), is_split_into_words=True)` 把**一个汉字当一个 word**，
再用 `word_ids()` 拿到每个 token 属于第几个汉字；只有每个汉字的**首个子词**背这个汉字的标签，
其余子词和 `[CLS]/[SEP]/[PAD]` 全部设 `-100`（`cross_entropy(ignore_index=-100)` 会跳过）。
不设的后果：同一个 span 的 loss 被重复算好几遍、标签计数被放大，模型会过度自信地往该类别偏。
推理时反过来，用保存下来的 `word_ids` 把子词级预测还原成字符级，才能拼回原文 span。

### Q4：为什么不让大模型直接输出 start/end 偏移？
因为生成的字符下标极不可靠：中文"字符数 ≠ token 数"、从 0 还是 1 数全凭模型心情、长文本还容易错一位，
**一旦错位整个 span 就废**。但"逐字抄一段原文"对模型很容易。
所以本项目约定：模型只输出**文本片段**，程序用 `text.find()` 反查位置；找不到说明模型编了原文没有的字，
offset 记 -1、并计入"幻觉论元"统计。代价是同片段多次出现时取首次、高亮位置可能偏——
评测只看 `(角色, 文本)` 是否一致，不受影响，这是**有意的近似**。

### Q5：一句话里有多个事件怎么处理？
本项目的 L2/L4 主实验刻意用**句子级单事件**子集（5,747/930，只取 `event_list` 长度=1 的句子），
因为这样 BIO 标注无歧义、指标干净。多事件在 L5 处理：
`detect` 数据保留全部句子 → 切句后逐句抽取 → **同类型事件在篇章内合并**成事件流、论元累加去重、
记 `sent_ids` 溯源。真实的多事件句（占 4.6%）在这种设计下会变成"多条事件流"，而不是被硬塞成一条。
课上用「北京市监局约谈美团、饿了么等 6 家平台」演示：一句话抽出 6 个「被约谈」事件。

### Q6：公告很长（最长 3,502 字）超过 BERT 512 怎么办？
本数据的篇长 p50 506 字、p99 2,696、max 3,502，确实超长。策略是**两级切分**：
篇章先按 `。！？；\n` 切句（保留字符偏移），每句单独送模型（句子级 p99 393 字，`max_len=256`
只截断极少数），抽完再把句内坐标加 offset 换回全文坐标。这样既绕开 BERT 输入上限，
又保留"能定位回原文"的能力；代价是跨句论元（比如金额在上一句、主体在这一句）会丢。

### Q7：检测集负样本 77.9%，你怎么避免模型退化成"全猜没事件"？
三个措施：① 采样分层保比例（`sample_stratified_detect`），直接截断很可能拿到全正或全负；
② 指标不只看 accuracy（78% 是多数类托底），必须看 P/R/F1 与混淆矩阵；
③ 检测指标报**全量与 clean 双口径**——本数据 dev 检测集与训练集文本重复 **9.2%**（487/5,302），
全量会虚高，clean（4,815 条）才代表真实泛化。

### Q8：规则基线论元 F1 只有 0.17，是规则写得太差吗？
不是"差"，是**任务决定的**。规则的失败分布很说明问题：触发词命中率 **99.8%**，但错误里
**55.6% 是"金额/日期填错角色"**（一句公告里好几个数字，规则不知道哪个属于哪个角色），
23.0% 是触发词边界不对，15.2% 是类型错（「质押」抢「解除质押」）。
也就是说：**规则擅长"有规律且唯一对应"的字段**，遇到"多候选、要语义判断"的角色就崩。
这个数字的价值在于给出"模型必须解决什么"的靶子，而不是证明规则没用。

### Q9：事件级 F1 只有 0.06，是不是模型很烂？
不是，是**口径极严**。`event_exact` 要求"类型 + 触发词 + 论元集合**完全相等**"才算对；
一个事件平均 4.38 个论元，漏一个或串一个角色就整条不算对。所以本项目同时报三级指标：
trigger（找词）、argument（填槽）、event_exact（整条），再配 per_type/per_role 定位瓶颈。
简历上只写 event F1 会显得很差，只写 argument F1 又会被质疑，**两个都写才是诚实**。
反过来，指标选错还会得出荒谬结论：规则基线的 type_macro F1 **0.8118** 反而高于 BERT 的 0.7654
（规则用触发词词典直接定类型），但论元/事件级上规则被碾压——**只报类型指标等于自欺**。

### Q10：为什么评测要自己做一套，不用现成框架？
因为现成的 NER 框架（如 seqeval）解决的是"实体边界"，而事件抽取要判的是
"类型 + 触发词 + 多个角色槽位"，且要区分三级口径。自建评测重在**口径唯一**：
所有方法只产出同一种预测 JSONL，指标只能由一个函数算；另外三条纪律写进代码注释——
预测键必须 `id|sent_id`（DuEE-Fin 的 id 是文档 id 不唯一）、解析失败的行保留空结果不删分母、
跨方案必须同批样本。第一版没做这三件事时，gold 对 gold 只有 0.93 F1。

### Q11：LLM 那边 JSON 合法率 100%，为什么还说格式是问题？
因为**格式合法 ≠ 字段合法**。实测 200 条里 JSON 全部可解析、0 修复，但 schema 不合规的角色
zero-shot 有 **4 个**、few-shot 有 **3 个**（第一版 prompt 把角色用 `/` 拼一行、和角色名自带的斜杠撞车，当时是 84 个），
另有各 **6 条**论元根本不在原文（幻觉）。所以生产系统必须有 schema 校验 + 原文 span 校验，
这两件事在 L5 的 `_validate()` 里实现，拦下来的样本进 `needs_review`。

### Q12：LoRA 的 loss masking 是什么？不 mask 会怎样？
SFT 的样本是 `prompt（system+user）+ 目标 JSON`。loss masking 就是把 prompt 部分的所有 label
置 `-100`，**只在目标 JSON 的 token 上算 loss**。不 mask 的话模型要花一半算力去"复述输入"，
loss 被长 prompt 稀释，学到的其实是"续写句子"而不是"输出结构化结果"。
配套的两个坑：① 目标后面**必须加 EOS**，否则模型学不会停；② prompt 太长把目标挤掉时
labels 会全是 `-100`，`loss = nan`——所以本项目 `max_length=1280` 而不是照抄 NER 的 384。

### Q13：8GB 显卡怎么跑 0.6B 的 SFT？显存都花在哪？
显存大头不是权重（0.6B bf16 ≈1.2GB），而是**logits**：`batch × max_len × 词表 151,936`。
`batch=4 × 1280 × 151936 × 2B ≈ 1.6GB`，上采样到 float 还翻倍 → 直接 OOM。
解法是组合拳：`batch_size=2 + grad_accum=8`（等效 batch 16）、`--grad_ckpt`（梯度检查点）、
`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 治碎片、`model.config.use_cache=False`。
实测峰值 **6.09 GiB**，LoRA 只训 **0.38%** 参数（2.29M/598M）。

### Q14：你这两套评测口径（dev 930 与 n=200）怎么保证可比？
n=200 不是"另外抽的 200 条"，而是**同一顺序的嵌套子集**：先把 dev 按 `(id, sent_id)` 排序再
`shuffle(seed=42)`，取前 200，n=150/n=100 就是它的前缀。这样：
① 小样本结果可以直接和大样本并排看；② 文件名无关、行序无关（排序之后再洗牌），换台机器也是同一批；
③ 抽样 id 落盘 `eval_ids.json`，判别式方法的全量预测再**投影到同这 200 条**报一份。
不这么做的真实后果：两个脚本都写 `seed=42`、但一个 `random.sample` 一个分层采样，实测几乎不重合。

### Q15：如果让你把这个系统真正上线，下一步做什么？
分四条线：**数据**——补真实长篇公告（本数据是 2019–2020 标题式短句），加"同串多次出现"的标注；
**模型**——span-based（Biaffine/GlobalPointer）替代 BIO 减少边界误差，给"角色-数值类型"加约束
（金额角色只收带"元"的、比例角色只收带"%"的）压掉角色串味；
**训练**——长尾类型（被约谈 53 条）加权采样/focal loss，SFT 从 1 epoch 增到 3 epoch 并保留内层验证选点；
**工程**——13 个专家模型量化/蒸馏成一个，`needs_review` 接人工平台，并按
"每 100 条能捞回多少错"衡量人审 ROI。

### Q16：这个项目里你印象最深的一个 bug 是什么？

硬约束解码「假生效」。当时我们给 CRF 加了解码期硬约束（把非法转移分数置 −1e4），评测出来的非法数和
软约束**一模一样（1,242 处）**，一开始还以为是统计口径问题。后来在 eval 里加了一句防御性打印
「已装载：禁止 N 个非法转移对、M 个非法起始标签」——输出是 **N=0**，才定位到根因：
约束矩阵在 `crf.py` 里注册成 **buffer（`persistent=True`）**，会跟着 checkpoint 一起保存；
checkpoint 是软约束训出来的（buffer 全 `True`），而我们「先装硬约束、再 `load_state_dict`」，
加载过程把约束**覆盖回全 `True`**，等于一条都没生效。
修法：`load_state_dict` **之后再装一遍约束**，并加 `if n_forbidden == 0: raise RuntimeError`。
修好后同一个模型论元 F1 从 0.5815 涨到 **0.6566**。
这件事让我养成了一个习惯：**凡是「约束/配置」类的东西，加载完要回读校验一遍再信它**。

### Q17：LoRA 为什么能反超 BERT+CRF？小模型不是更弱吗？

因为**这个任务的主要难点不在「语言理解」，而在「输出格式与标注口径」**：要把一句公告变成
`{"events":[{"type","trigger","arguments"}]}`，还要知道金标把「9.18万」而不是「9.18万股」当论元。
BERT+CRF 受限于固定标签空间（149 个）和 BIO 边界；而 Qwen3-0.6B 经过 LoRA 微调后：
① 输出空间是全部词表，能逐字生成任意 span；② 从 3,499 条训练样本里**直接学到了标注口径**。
实测：零样本 argument **0.1129** → LoRA **0.6971**（n=200），反超硬约束 BERT（0.6418）**5.5pp**；
只训 **0.38%** 参数、2,327 s、峰值 4.0 GiB。
但它的短板也清楚：event_exact **0.1850 < 0.2268**（边界精确性不如序列标注）。
所以结论是「**生成式召回强、判别式边界准**」，而不是「谁取代谁」。

### Q18：两段式为什么反而更差？

先看诊断再下结论：检测器 F1 **0.7740**、类型准确率 **0.9452**（只错 51 句），两段本身没问题；
端到端却只有 **0.3690** 论元。原因是**训练预算被切碎**——13 个类型专家每个每 epoch 只有 3~31 步，
3 epoch 才 90 步量级，而联合模型有 486 步。
给足训练预算时两段式的标签空间更小、论元理论上能更准；但**工程上先要算清训练步数预算**。
这也是「拆得越细越好」最容易翻车的地方：**每个子模型都要足够的训练信号**。
